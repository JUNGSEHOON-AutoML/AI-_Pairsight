# 신뢰 출처 RSS 해시 색인 (설계)

작성일: 2026-10-19 · 확인 목록: [rss-collection-checklist.md](rss-collection-checklist.md) · 코드: `web/lib/index/`, `web/lib/providers/rss-index.ts`, `web/scripts/index-collect.ts`

## 목적과 범위

Google Vision 같은 유료 역이미지 검색 대신, **신뢰 출처가 공식 RSS로 공개한 기사 사진**의 지각 해시를 모아 둡니다. 들어온 이미지와 비슷한 사진을 이 색인에서 찾아 **원본 후보**로 넘깁니다.

- **색인은 후보를 제안할 뿐 판정하지 않습니다.** 찾은 후보는 기존 파이프라인을 그대로 거칩니다: 후보 페이지를 robots를 지켜 실제로 확인 → 정렬 이미지 비교 → 판정 규칙.
- **사용하지 않는 것:** 사이트맵, 링크 따라가기, 과거 기사 목록 페이지, 웹 검색, 봇 차단 우회.
- **수집하는 것:** 피드에 지금 올라와 있는 항목만. 피드는 보통 최근 20~50건이라, 과거 기사를 대량으로 모을 수 없습니다(의도된 제한).
- **허용된 피드만 수집합니다.** `trusted-sources.json`의 `feeds[].status`가 `allowed`인 피드만 대상입니다. 2026-10-19 기준 허용 피드는 0개입니다(확인 목록 참고).

## 한계 (문서와 결과 화면에 명시)

- **수집을 시작하기 전에 게시된 사진은 찾을 수 없습니다.** 맥락 조작의 전형인 "몇 년 전 사진 재사용"은 대부분 이 색인 밖입니다. 그런 사례는 사람이 원본 후보를 지정하는 방식(평가 하네스 `sourceUrls`)이나 다른 검색 수단이 필요합니다.
- RSS에 이미지가 없는 기사는 색인되지 않습니다. 기사 페이지를 따로 열어 대표 이미지를 가져오지 않기 때문입니다.
- 색인 대상은 허용된 출처뿐이므로, 신뢰 출처 목록 밖의 원본은 찾지 못합니다.
- 결과 화면 문구(검색한 곳): "신뢰 출처 RSS 색인 (YYYY-MM-DD부터 수집). 그 전에 게시된 사진은 찾을 수 없어요."

## 수집

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 주기 | 피드당 **60분에 1회** 권장 (cron 등 외부 스케줄러로 `npm run index:collect`) | 피드가 짧아서 놓치는 항목이 생기면, 주기를 줄이기 전에 출처의 `<ttl>`·`Cache-Control`을 먼저 확인 |
| 출처별 속도 | 같은 출처(origin)에 **2초에 1요청**. robots `Crawl-delay`가 더 길면 그 값 | 피드와 이미지 호스트(CDN)는 서로 다른 출처로 따로 계산 |
| 실행당 상한 | 피드당 새 항목 **최대 30건**의 이미지만 처리 | 첫 실행에서 피드 전체를 한 번에 받는 정도 |
| robots | 피드 URL과 이미지 URL 모두 해당 출처의 robots.txt를 확인(1시간 캐시). 금지면 건너뜀 | 앱의 `PolicyFetch` 그대로 |
| 차단·오류 | 403/429/503·봇 확인 페이지·robots 금지 → **그 출처는 이번 실행에서 즉시 중단.** 429/503은 `Retry-After`(최소 60초)를 지킴. 다른 신분·프록시로 재시도 안 함 | |
| 요청 | 쿠키·로그인 없음. User-Agent `PairsightBot/0.2 (on-demand image verification)` | 운영 시 연락처 URL 추가 필요 |
| 이미지 | 메모리에서만 해시 계산 후 즉시 버림. 10MB·2천만 픽셀 제한 | 디스크·로그에 저장하지 않음 |

이미지 URL은 RSS 안에서만 찾습니다. 우선순위는 `media:content`(image) → `media:thumbnail` → `enclosure`(image/*) → 설명(`description`/`content:encoded`) 안의 첫 `<img>`입니다.

## 저장 (기사 본문·이미지 파일은 저장하지 않음)

`web/.data/rss-index.jsonl`에 한 줄에 사진 하나씩 저장합니다(git에 올리지 않음). 같은 `articleUrl` + `imageUrl`은 한 번만 저장합니다.

```json
{"v":1,"sourceId":"yonhap","articleUrl":"https://…","publishedAt":"2026-10-19T09:00:00+09:00","imageUrl":"https://…","hashes":{"full":"c3a1…","center":"9f02…"},"collectedAt":"2026-10-19T10:00:00Z"}
```

- **`full`:** 이미지 전체의 pHash입니다(앱의 이미지 비교와 같은 64비트 DCT 해시).
- **`center`:** 가운데 70%를 잘라낸 영역의 pHash입니다. **잘라내기에 강한 보조 해시**로, 가장자리를 잘라낸 재공유본도 찾기 위해 둡니다.
- 메타 파일 `web/.data/rss-index.meta.json`에 `startedAt`(첫 수집 시각), 피드별 마지막 실행 결과를 남깁니다. 결과 화면의 "YYYY-MM-DD부터 수집"이 이 값입니다.
- 제목·요약·본문·캡션은 저장하지 않습니다. 화면에 필요한 정보는 판정 단계에서 후보 페이지를 다시 확인할 때 얻습니다.

## 검색 (`RssIndexReverseSearch`, `ReverseSearchProvider` 구현)

1. 들어온 이미지의 `full`·`center` 해시를 계산합니다.
2. 색인의 각 항목과 네 가지 조합(full↔full, full↔center, center↔full, center↔center)의 최소 해밍 거리를 구합니다.
3. 거리 **≤ 10**(63비트 중)인 항목 중 가까운 순으로 **최대 5개**를 후보로 반환합니다. 이 임계값은 후보를 넓게 잡는 용도라서, 판정용 임계값(정렬 후 ≤18 + 상관도 ≥0.9)과 별개입니다.
4. 후보에는 `imageUrl`(비교할 사진)과 `discoveredAt`(RSS 게시일, 약한 날짜)을 붙입니다. 판정에 쓰이는 날짜는 후보 페이지를 다시 확인할 때 페이지 메타데이터에서 얻습니다.

**규모:** 단순 선형 탐색입니다. 허용 피드 수십 개 × 하루 수백 건 정도라 수만 건까지는 충분합니다. 그 이상이면 BK-tree나 해시 분할 색인으로 바꿉니다.

## 법적·운영 주의

- RSS 안내에 상업 이용 금지가 있는 곳은 **해시만 저장해도 수집하지 않습니다.** 이미지를 내려받아 처리하는 행위 자체가 피드 이용이기 때문입니다.
- 이용 허락을 받은 경우에도 저장 범위(URL·날짜·해시)와 보관 기간, 삭제 요청 처리 방법을 허락 범위에 맞춥니다.
- 출처가 피드에서 항목을 내리거나 삭제를 요청하면, 해당 `articleUrl` 줄을 지우는 정리 작업이 필요합니다(미구현).
